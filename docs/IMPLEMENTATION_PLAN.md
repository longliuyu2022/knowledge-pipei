# 合并实施、迁移与验收

日期：2026-09-13。本文件保留实施时的技术蓝图；当前应用、数据库迁移与新域名部署已完成，实际落地范围见 [RELEASE.md](RELEASE.md)，运行路径见 [DEPLOYMENT.md](DEPLOYMENT.md)。结构建议和全量切站计划不等于当前部署状态。

## 1. 采用的技术路线

以同频现有 React 19 / TypeScript + Vite 前端、Express 5 + Node SQLite + SSE 后端为主干，按模块迁入同题。保留已验证的行为与测试，统一组件、身份和权限。后端沿用现有 JavaScript 模块，先完成业务边界，避免为了类型迁移同时重写全部逻辑。

首版使用单应用、单服务、独立 SQLite 数据库与持久任务表。SSE 只传变更通知，业务状态、未读和待处理任务以数据库为准。任务执行使用租约和幂等键；服务重启后恢复过期租约。需要多实例时再迁入 PostgreSQL 与共享队列，首版不先引入微服务。

建议结构：

```text
/root/xiangmu/
  zhihu-tongti/                 现有同题
  fanganer/                     现有同频
  zhihu-tongzhi/                合并项目（已实现的独立应用）
    src/
      app/                     导航、页面框架、通用组件
      features/
        questions/             问题发现和问题详情
        circles/               成员、轮次、讨论、资料与成果
        profiles/              知识报告和授权
        matching/              伙伴提案与小组推荐
        conversations/         私聊、AI 话题及 AI 伙伴
        notifications/         站内通知
        admin/                 用户、画像、治理和任务状态
    server/
      modules/                 与业务边界对应的路由和服务
      integrations/            知乎与模型适配器
      jobs/                    匹配、主持、审核、通知、画像建议
      db/migrations/           可核对的 schema 版本迁移
    shared/                    标签、权限定义、接口契约
    tests/                     权限、状态机和集成验证
    scripts/migration/         只读预演、导入、校验与回滚工具
```

代码迁入时不复制 `.git`、数据库、运行时会话、`.env*` 私密配置、依赖、构建物或私有验收记录。必要配置用占位模板和受控服务端凭证引用。模型适配统一沿用同频当前已验证的渠道和可配置模型，不同时保留两套隐式模型回退链。

正式 origin 已由用户指定为 `https://zhihu.aiimage.icu`。本轮先使用 Caddy 托管独立筹备说明页；应用合并完成后将相同站点配置替换为新服务的反向代理，不沿用该域名此前的知识赛车跳转。

## 2. 复用边界与必须重构的部分

以下路径相对对应来源根目录。基线版本见 [README](../README.md)。

| 模块 | 来源证据 | 实施决策 |
| --- | --- | --- |
| 知乎 OAuth 与数据检查 | 同频 `server/zhihu.js`、`server/zhihu-validation.js`、`server/app.js` | 统一使用这套已实测流程，保留 state、会话绑定和授权竞态检查 |
| 画像与解释 | 同频 `server/matching.js`、`server/ai.js`、`src/ProfilePage.tsx` | 迁入证据结构，增加知识报告、版本和可见范围 |
| 私聊与幂等发送 | 同频 `server/store.js`、`src/ConnectionsPage.tsx` | 保留参与方和屏蔽校验；聊天与邀请主键关系在迁移中显式映射 |
| 破冰权限 | 同频 `server/conversation-context.js` | 保留每次外部 await 后重新检查会话、双方画像版本与屏蔽 |
| 在线队列 | 同频 `server/pairing.js` | 新建异步状态机；仅参考筛选和配对原子性，不沿用 Map 作为长期状态 |
| 小组讨论与成果 | 同题 `server/store.js`、`server/app.js`、`server/ai.js` | 迁移加入、回复、主持、成果版本、引用和可见性；补轮次状态机 |
| 官方来源 | 同题 `server/zhihu.js` | 迁移结果缓存、并发去重与绑定请求成员的临时来源标识 |
| 邮箱账号 | 同题 `server/auth.js`、`server/store.js` | 兼容现有密码哈希和账户状态，整合到账户身份表 |
| 后台 | 同频 `server/admin.js` + 同题账号停用及举报处理 | 一个后台，区分运营统计、站点管理和小组主持权限 |
| 前端样式 | 双方 `src/` | 统一导航、色彩和组件；按功能隔离 CSS，避免直接拼接全局样式 |

不能直接复制整个数据库：双方都有 `users`、`sessions`、`messages`，但字段和语义不同。同频 `messages.conversation_id` 指向已接受的邀请；同题消息归属小组且有回复、来源和派生依赖。

同频当前邀请要求双方在全站发现中可见；新设计要将「同意匹配」「允许组内邀请」「公开画像」分离。否则从小组进入私聊会无故要求用户公开资料。

同题现有成果可标为编辑者核对，不能直接映射成全员同意。参与描述和阶段字段也不能代替服务端校验的轮次状态机。

已核实同题 `store.addUpdate()` 中的 `next-topic` 会直接改写 `communities.question`；现有接口允许已加入成员触发，历史发言和成果并未分轮保存。新模型把开启下一轮作为有明确主持权限的状态变更，旧轮只读保留。历史数据不能可靠恢复问题归属时，归入标明来源的历史讨论区，不通过 AI 猜测分轮。

迁移必须保留并重写同题 `messages` / `artifacts` 中的 `dependency_ids`、`citations.messageId`、`source_ids` 及成果的 `origin_message_id`。现有逻辑在依赖被隐藏或被当前用户屏蔽时，将整项 AI 输出或成果设为不可见，并禁止编辑、导出；遗漏依赖字段会破坏这项保护。

`dependency_ids` 包含全部进入模型上下文的真人消息，不能缩减为最终被引用的消息。旧成果只保留当前正文并递增 `version`，没有完整旧版本正文；新的修订历史从迁移快照开始，无法恢复的历史不伪造。

同题使用同源 JSON 写请求校验，同频额外使用 CSRF token；合并后的所有写接口及前端请求统一接入同频的 CSRF 协议。同题普通会话上的 `site_role` 与同频独立管理员会话不能直接拼接，要经过统一角色授权。迁入邮箱密码时保留旧 `scrypt-v1` 校验器的字节语义：旧盐作为十六进制文本输入，不能先解码为字节后改变校验结果。

屏蔽关系保留方向。同题当前主要做单向消息过滤，其成员列表、资料和进展未全面跟随屏蔽；新版本需补齐本人视图中相关内容的隐藏和派生依赖处理。对邀请、匹配和私聊则检查任一方向的屏蔽并阻止建立或继续联系，小组内屏蔽不自动踢出对方。

## 3. 统一领域模型

| 领域 | 建议实体 | 关键约束 |
| --- | --- | --- |
| 身份 | `users`、`identities`、`sessions`、`roles` | 用户和知乎／邮箱登录方式分离；外部 ID 保留字符串精度 |
| 知识画像 | `profile_versions`、`profile_claims`、`evidence`、`consents` | 判断关联证据、来源与授权版本；公开视图单独生成 |
| 问题 | `questions`、`circles`、`discussion_rounds` | 问题标识规范化；同问题可有不同目标和阶段的小组 |
| 参与 | `memberships`、`member_preferences` | 成员角色、有效期、关注和提醒设置分开 |
| 讨论 | `circle_messages`、`sources`、`outcomes`、`outcome_revisions` | 引用只能指向可访问的本范围内容；保留依赖清单 |
| 匹配 | `match_requests`、`match_proposals`、`match_slots` | 一人一个有效请求和一个待确认提案，双方确认事务化 |
| 私聊 | `connection_requests`、`connections`、`private_messages` | 群内邀请与后台匹配共用连接；参与方、屏蔽、幂等校验统一 |
| 任务与提醒 | `jobs`、`outbox_events`、`notifications` | 状态变更与事件同事务；持久通知、去重、租约恢复 |
| 治理 | `blocks`、`reports`、`moderation_cases`、`sanctions`、`audit_events` | 处罚范围、期限、理由和申诉记录明确；平台与小组权限分离 |
| 来源迁移 | `legacy_id_map`、`migration_runs` | `(source_project, entity_type, old_id)` 唯一，重跑不重复导入 |

以上是领域拆分建议，不要求每个实体首版都形成独立文件或复杂服务。先锁定权限和外键，再实现最小可用字段。

统一身份不能只看昵称、头像或邮箱文本。只有已经验证可跨应用对齐的知乎稳定标识才可自动关联；两个旧实现可能保存不同形式的 `uid` 或 `hash_id`，需要验证映射。邮箱未经归属验证时不自动合并，用户分别验证旧账号控制权后再绑定。无法确认的保留为独立身份。

具体差异已确认：同题存储 `hash:<hash_id>` 或 `uid:<十进制 uid>`，同频 `subject` 存储裸 `hash_id` 或 `uid`。迁移记录标识类型及来源，核实后按类型对齐，不能直接比较原字段或不区分类型地去前缀。普通实体 ID 也用来源命名空间映射，同题固定启动小组 ID 与带前缀 UUID 一并处理。

## 4. 后台匹配与任务调度

请求状态建议为 `searching / paused / proposed / fulfilled / cancelled / expired`；提案有独立的双方确认时间及 `pending / accepted / declined / cancelled / expired`。轮询、离线和重新打开页面都不自动创建新请求或续期。

创建提案时在事务中检查有效请求、许可版本、屏蔽、既有连接、账号状态和画像版本，并取得双方唯一活动槽位。两个确认满足条件时只创建一个连接；过期、取消与第二次确认的竞态按数据库条件更新决定结果。

匹配计算先用本地主题、问题、目标、阶段和节奏特征；模型用于解释及话题补充。队列扫描不发外部请求。后续增加 embedding 时明确实际算法来源，有服务故障时如实回退。

持久任务至少具备：任务类型、所属范围、执行时间、幂等键、状态、重试次数、租约到期、输入版本和取消原因。服务启动恢复任务；所有写回检查最新账号、授权、成员和画像状态。对响应结果未知的外部请求不盲目重试，避免重复扣费或重复消息。

通知先持久化，再通过 SSE 告知在线会话。未读计数不因查看其他页面误清；取消的提案即使存在旧通知也不能再接受。Web Push 是 P3 的独立通道，浏览器通知权限由用户主动开启。

统一服务必须共用现有上游频率预算，不能让画像、主持、破冰、审核分别拥有互相不知情的 5 RPM。采用优先级：安全待审核、用户主动请求、低频自动主持与画像建议；同范围任务合并，设置并发和每日预算。模型不足时延后自动任务或显示规则结果。重点 AI 审核的积压不得改为默认放行。

## 5. 引用、权限与数据撤回

每次模型输入由后端按本次功能和当前访问者组装最小集合，不直接传完整用户对象、会话对象或整库聊天。知乎搜索摘要、用户摘录和实际原文分别标记，模型输出的引用 ID 必须来自本次允许的输入。

通用鉴权覆盖群聊、私聊、推荐、搜索结果加入、AI、导出和后台。AI 及缓存保存依赖的画像版本、成员权限、授权版本、消息与资料 ID；输出读取时复查。群内屏蔽后的可见范围可能因观看者不同而变化，不能用一个不区分权限的摘要缓存直接广播给所有人。

新建「聊天改善画像」流程时，将本人选择的材料先转为待确认建议，正式发布需再次确认。撤回后同时处理未执行任务、处理中结果、建议、索引和缓存；保留仍有其他有效证据支持的判断时，重新计算其来源说明。

用户注销和清除数据策略需在首版实现：私有画像、导入、匹配请求和授权删除；共同讨论按已告知的策略删除或去标识，受影响的引用与派生内容失效。备份采用受控保留期和到期清理，恢复时重放删除记录，避免把已删用户重新发布。常规日志不记录消息原文或令牌；治理案件只保留必要片段，访问有审计，建议默认 30 天后清理。

## 6. 数据迁移与上线顺序

1. **先做独立空库开发。** 新目录使用独立数据库、cookie 名和服务配置；用明确标注的测试数据验证功能，不把演示人物导入真人池。原服务继续运行。
2. **制作一致性备份。** 实施时使用 SQLite backup API 或等效一致性快照，不能只复制运行中 WAL 数据库的主文件。验证恢复和备份权限。
3. **离线迁移预演。** 从只读快照导入新库，为账号、小组、消息、邀请、来源、成果生成映射。全部外键和 JSON 内引用一并改写；行号游标、未读位置和活动计数重新核对。
4. **保护既有隐私。** 原有注册方式、密码哈希、账号停用、成员角色、屏蔽、待处理举报和成果可见性保留。私有资料默认仍私有；迁移数据不自动构成新用途授权。旧用户下次登录确认新隐私选项后才进入新匹配或分析功能。
5. **不搬运会话与 OAuth 令牌。** 用户在新应用重新登录；访客需要在原会话仍有效时绑定或领取一次性迁移凭据，无控制权的访客账号不得仅凭昵称认领。旧邮箱密码可兼容校验，不传明文。
6. **新环境验收。** 使用独立本机空闲端口和预览部署，完成双人异步匹配、跨小组权限、AI 引用和撤回测试。新的公网 origin、cookie、安全头及准确登记的回调按实际部署配置。
7. **在正式切换窗口处理增量。** 旧站临时停止写入，执行最终快照／增量迁移，校验数量与引用后切换；不让两套数据库长期同时写同一批用户关系。旧链接通过映射跳到正确新页面，不自动加入小组。
8. **保留回滚能力。** 切换前失败可直接恢复旧站写入；新站已产生写入后不能直接覆盖回旧快照，需先冻结并保留增量，执行数据回补或优先修复。回滚演练必须包含这一差别。

新域名已确定为 `https://zhihu.aiimage.icu`，独立仓库尚未设定。建议新回调为 `https://zhihu.aiimage.icu/auth/callback`，用户已经确认登记该回调；最后的真实授权仍需用户本人完成。实施时先与赛事登记逐字符核对，随后由用户亲自完成最终授权。现有同频真实 OAuth 验收可作回归基线，同题此前的 OAuth mock 结果不能当成真实联调。

## 7. 分阶段交付与并行边界

| 阶段 | 交付物 | 放行条件 |
| --- | --- | --- |
| P0 合并基础 | 独立应用、统一导航／身份／标签／权限、schema 与迁移预演工具 | 两种账号可访问原有能力，数据隔离、来源映射和权限回归通过 |
| P1 完整主流程 | 问题入口、轮次与参与期、知识报告、小组推荐、异步配对、双确认、来源破冰、阶段成果、基础及重点 AI 治理 | 一套账号走通问题到成果及知识连接；重启不丢匹配；撤回和屏蔽生效 |
| P2 深度体验 | AI 知识伙伴、自我对话、授权聊天更新建议、可用样本下的趋势、主持与审核策略优化 | AI 身份清楚，数据来源及撤回可追踪；真实试用反馈驱动调整 |
| P3 扩展 | 知乎页面扩展入口、Web Push、必要的多实例能力 | 对应平台／浏览器权限与规模需求明确，独立验收 |

首个里程碑选 P0 + P1，让两套产品已经形成完整价值路径，再补 P2。这些是按依赖划分的工程工作包，不承诺未经评估的固定开发天数。

可以安排三个并行任务：

- **小组线：** 问题、轮次、参与和成果 UI，复用同题讨论服务。
- **画像与连接线：** 知识报告、同频提案 UI、深度破冰和小组到私聊。
- **基础与治理线：** 统一身份、数据库迁移、后台任务、授权、举报与通知。

主集成者先锁定 API 契约、权限和 schema，维护公共入口与集成验证。并行任务只修改各自目录；共同的 `app`、schema、类型、样式变量和路由注册由一个负责人合入，避免多个代理直接复制覆盖。核心权限和基础契约完成后才推进依赖它们的端到端流程。

## 8. 有意义的验收清单

| 场景 | 必须证明的结果 |
| --- | --- |
| 来源迁移 | 两库各类记录数量和引用可核对；重复导入不增记录；未知身份不被错误合并 |
| 成员有效期 | 临时到期或退出立即失去成员数据访问，停止提醒；不会自动判定小组已解决 |
| 阶段成果 | AI 结论、分歧和引用正确区分，编辑冲突不覆盖，未核对成果不标为共识 |
| 异步匹配 | A 离线后 B 仍可被匹配；服务重启恢复任务；双方在不同时刻确认后只建立一个连接 |
| 竞态 | 取消与确认、屏蔽与发消息、画像更新与 AI 回写、退出与摘要生成均不能越权 |
| 数据边界 | 未加入者看不到成员讨论；未确认者不能私聊；私有导入不会出现在另一人的话题或报告 |
| 断网与通知 | 重连恢复持久状态，提案通知不重复，草稿不跨会话串用，不把站内消息当离线系统推送 |
| 安全治理 | 骚扰与重复联系样例进入处理，正常知识争论不被直接封禁；高风险审核故障不默认放行 |
| 授权撤回 | 关闭聊天分析后新任务不再执行，在途输出不回写，相关建议及缓存不再可见 |
